**Repository survey: LLM-driven generation of individual 3D objects**

Survey date: 19 October 2026. Scope: image or text input, an LLM that produces procedural geometry code, and execution in Blender or Three.js. Findings come from repository documentation and selected source files; these systems were not installed or benchmarked. “Local application” and “local model inference” are recorded separately.

The most useful starting references are img2threejs for image-to-code with a structured intermediate representation, BlenderLLM for local text-to-Blender inference, threejs-generator for an application interface, and 3DCodeBench for controlled experiments. This is a judgment about their fit to this project, not a measured ranking of output quality.

**Notes on the strongest matches.**

img2threejs turns an image into an ObjectSculptSpec JSON component description, then builds and reviews successive Three.js passes. It includes deterministic validation scripts, comparison sheets, and a browser-based visual review workflow. It is a skill/tooling repository that needs an agent host, vision access, and browser tooling, rather than a standalone inference server. Its default procedural route is the relevant one; the separate hosted mesh-generation plugin would test a different approach. This is particularly useful for the project's proposed two-stage architecture. [README](https://github.com/img2threejs/img2threejs), [architecture and entry-point scripts](https://github.com/img2threejs/img2threejs/blob/main/docs/ARCHITECTURE.md).

BlenderLLM releases a model, training data, benchmark, and inference/rendering code. Its model is text-only, so image input would require an added perception stage. Start with modeling.py, scripts/infer.py, and scripts/blender_runner.py: the flow generates a script, exports OBJ, then renders views through background Blender. The checked inference helper defaults to 512 generated tokens, which should be reviewed for longer objects. The released example does not implement an automatic render-and-revise loop. Local inference is directly supported; an HTTP model-serving layer or quantized deployment would be additional integration work. [Repository](https://github.com/FreedomIntelligence/BlenderLLM), [inference](https://github.com/FreedomIntelligence/BlenderLLM/blob/main/scripts/infer.py), [runner](https://github.com/FreedomIntelligence/BlenderLLM/blob/main/scripts/blender_runner.py).

threejs-generator provides a local web workbench with generated createAsset() JavaScript, editable procedural controls, saved assets, and GLB export. The documented model connections use remote providers; running the application locally does not imply local LLM inference. Its documented input is text, so image conditioning needs to be added. It preserves the previous working asset when generation fails. This is a useful UI starting point, with a small project history and no independent quality evidence established by this survey. [Repository and setup](https://github.com/wearywas/threejs-generator).

3DCodeBench directly targets object generation through Blender code. It includes 212 categories, text/image tasks, traceback-feedback retries, agent wrappers, and executability, image, and shape metrics. The reference assets derive from Infinigen but are distributed as standalone scripts, avoiding the need to construct full scenes for each trial. Its image task expects reference views to be prepared; a one-photo experiment should be configured explicitly. The inspected provider module implements Gemini, Anthropic, and OpenAI adapters, so local-serving support should not be assumed. [Repository](https://github.com/gaoypeng/3dcodebench), [provider implementation](https://github.com/gaoypeng/3dcodebench/blob/main/core/providers.py).

**Other useful references and their limits.**

BlenderGPT is a compact example of prompt → OpenAI call → generated Python → execution in Blender. It is useful for establishing a simple baseline. Its documented interface accepts text, and its older API/model integration needs compatibility checking. It does not provide the full image-perception and visual-evaluation pipeline needed by the proposal. [Repository](https://github.com/gd3kr/BlenderGPT), [add-on source](https://github.com/gd3kr/BlenderGPT/blob/main/__init__.py).

BlenderAlchemy uses an edit generator and state evaluator to search over script changes using rendered feedback. It starts from a Blender file and editable script, making it most relevant after initial object creation. The setup documents optional Ollama calls, but a completely local visual loop still requires a suitable vision model and configuration. Reproduction involves TaskSolver and an older pinned Infinigen commit. [Repository and setup](https://github.com/ianhuang0630/BlenderAlchemyOfficial).

LLM4Blender connects the Blender Text Editor to Ollama for Python generation and rewriting. It is a small integration reference, with Blender 4.0+ and an Ollama endpoint documented as prerequisites. The README does not establish a reference-image-to-object pipeline, automatic visual scoring, or export orchestration. Its image-prompt-writing feature should not be confused with image understanding. [Repository](https://github.com/tin2tin/LLM4Blender).

MCP for Blender, formerly blender-mcp, supplies Python execution and visual inspection to an external agent. For this project, use its procedural code path and constrain the task to one object. It also offers asset imports and dedicated 3D generators; those routes should be excluded when measuring LLM-written geometry. The bridge does not itself provide a local model or a complete autonomous reconstruction algorithm. [Repository and tool descriptions](https://github.com/ahujasid/mcp-for-blender).

LL3M is closely related research: specialized agents plan, retrieve API knowledge, generate code, debug, and refine geometry and materials. However, the public release is a client for the authors' service. The current README explicitly says the LL3M server was discontinued after retirement of the model used in the paper. Reimplementing its orchestration is a separate task; cloning this release is not sufficient for a runnable baseline. [Repository and service notice](https://github.com/threedle/ll3m).

For implementation, I would prioritize an API-backed single-object prototype, using img2threejs as the structured-specification reference or a small Blender runner as the execution layer. Add BlenderLLM as a local text-to-code comparison if suitable inference hardware is available. Use threejs-generator when a working browser application is the immediate priority, and adapt 3DCodeBench when reproducible evaluation is the priority.

For the project's direct-versus-two-stage comparison, keep the renderer, model, object set, camera, lighting, and inference budget fixed. Compare image → code against image → geometric JSON → code. A text-only local model belongs behind the same fixed perception stage when comparing code generators; otherwise differences in perception and coding become confounded.

My suggested pilot is 20–30 single objects across mugs, bottles, tables, chairs, lamps, and boxes, with several trials per object. Record successful execution, required parts, proportions, silhouette agreement, visible color/material agreement, latency, token cost, and repair count. Check another view as well as the input camera. Report traceback repair and visual refinement separately, since executable code can still produce the wrong object. These are proposed experiments, not measured results from this survey.

Scene-layout systems and dedicated image-to-mesh generators are outside the primary comparison. A Three.js viewer alone does not establish that a system generates Three.js geometry; the LLM must actually produce code or a structured specification that constructs the object.
